## Vercel backend

Use a dedicated FastAPI Vercel project with **repository root `.`**.
The root `vercel.json` targets the backend; it is not a combined Next.js deployment.
The existing static frontend/Pages build remains a separate deployment.

- Python is constrained to 3.12 in `pyproject.toml` and `.python-version`.
- Vercel loads `apps.api.main:app`; do not set the root to `apps/api`.
- `pyproject.toml` declares runtime dependencies and installs the vendored engine
  as a non-editable local package. The pip/Docker path uses
  `apps/api/requirements-runtime.txt`. Keep the two in sync.
- Build command: `python scripts/build_backend.py`, after dependency installation.
  Both JPL and Swiss files are checksum-verified, reused if present, downloaded
  only during a fresh build, and explicitly included in the function.
- The local package wheel carries its rules JSON; the JPL kernel is a separate
  repository-relative runtime resource. Localization JSON and services are included.
- Frontend source/assets, node_modules, development output, docs and tests are
  excluded from the Python function. Inspect the actual preview bundle before
  promotion; the local checks do not prove Vercel's final bundle size.
- Function duration is 60 seconds, but the browser deadline remains 30 seconds.
  Do not treat the platform duration as permission to exceed the UI deadline.
- Leave dashboard install/build overrides unset, or match the checked-in settings.
  No runtime downloads or durable filesystem writes are required.

Server-only configuration: `SUPABASE_URL`, `SUPABASE_ANON_KEY` (a publishable
or legacy anon key), `SUPABASE_SECRET_KEY` (preferred), and `WEB_ORIGINS`.
The existing `SUPABASE_SERVICE_ROLE_KEY` remains supported. Modern
`sb_secret_` keys use only `apikey`; legacy service-role JWTs also use Bearer.
User JWT verification remains a separate call with the public key and user's token.

Frontend build-time values stay `NEXT_PUBLIC_SUPABASE_URL`,
`NEXT_PUBLIC_SUPABASE_ANON_KEY` (accepts publishable keys), and
`NEXT_PUBLIC_API_URL`. Enter real credentials securely in host settings; do not
copy them into source, logs, chat or public-prefixed settings.

Configure exact frontend CORS origins and Supabase sign-in/recovery redirect URLs,
then exercise Google/email auth, recovery, profile CRUD, both methods, export,
admin history and deletion on preview with two ordinary accounts.

## Calculation and interface changes

The calculation-method preference is saved in localStorage and shared by chart,
today and compatibility pages. Valid explicit method URLs override that
preference; manual selection updates such a URL. No profile data is stored there.
Unknown-time onboarding's disclosed Swiss choice persists, while an explicit JPL
choice still receives JPL's documented birth-time requirement.

Compatibility responses are accepted only for the current request generation.
Changing either profile or the method invalidates pending results and errors,
clears old chart selection text, and allows a new request. Selecting the second
profile as first clears the invalid duplicate pair.

Swiss now uses the same pinned tzdata civil-time conversion and confirmed-fold
semantics as JPL. Its cache version is bumped to avoid reusing old timezone
results. Unknown-time Swiss remains an explicitly disclosed local-noon reference;
civil-day bounds handle midnight DST gaps. Swiss's daily transit snapshot remains
12:00 UTC; this documented calculation convention is not changed into a JPL scan.
No planetary formula, aspect rule or JPL vendor source was changed.

## Timing and validation limits

`docs/JPL_PERFORMANCE.json` records three fresh-process synthetic measurements;
rerun with `.venv/bin/python -m scripts.benchmark_jpl`.
Observed local daily calculations: cold 0.28–0.38 s, warm 0.02–0.05 s,
four concurrent distinct profiles up to 0.91 s each (including lock wait).
These are adapter timings, not API or Vercel latency. Hosted cold/warm checks must
include auth, database and HTTP overhead within 30 seconds. The global JPL lock
still serializes work per process; per-profile locks and caches do not coordinate
multiple instances. No distributed work deduplication is claimed.
